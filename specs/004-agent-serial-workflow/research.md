# Research: Agent Profiles + Serial Hermes Workflow (F5)

**Feature**: `specs/004-agent-serial-workflow/spec.md` | **Date**: 2026-10-15

No `NEEDS CLARIFICATION` items remain (the 2026-10-15 operator session settled abort/retry, tool scope, test strategy, and the quota gate; the model strategy is pinned by the already-PASSED pre-flight). Research below resolves the implementation choices the plan depends on. Verified facts come from the pre-flight evidence (`.agent/pi/f5-preflight/2026-10-15T21-48-43-554Z_4af17e/report.json`) and from read-only inspection of the installed CLI (`hermes --help`, `hermes chat --help`, `hermes usage --help`, `hermes config get model`) — no pre-flight re-run, no model call made during planning.

## 1. Hermes integration = subprocess CLI adapter (no SDK, no second framework)

- **Decision**: F5 executes agents by spawning the installed Hermes CLI (`hermes chat -Q --oneshot --query-file <path> --format stream-json -t <toolsets> --max-turns N --run-budget SECONDS`) — one process per agent step, spawned with `subprocess.Popen` (argv list) run **synchronously** inside the runner's worker thread: the `AgentExecutor.run` protocol method is a plain sync function, and there is no `asyncio` anywhere in F5 (matches §4's single-worker-thread design). Task text is passed via a temp `--query-file` (the CLI documents it as "safe for arbitrary text: nothing is shell-interpreted"), never via `-q` string interpolation and never through a shell.
- **Rationale**: The pre-flight proved exactly this surface works end-to-end on this machine (real API call 15s wall, real `terminal` tool round trip 12s wall, tool exec 65ms). `hermes chat` exposes every control F5 needs: toolset restriction (`-t`), turn cap (`--max-turns`), time budget (`--run-budget`), quiet programmatic mode (`-Q`), and machine-readable output (`--format stream-json`). Hermes stays the sole executor; our code is only a coordinator around a process boundary — structurally incapable of becoming a second agent framework.
- **Alternatives considered**: (a) Hermes Python SDK/package import — rejected, the install is docker-backed (`/opt/hermes`) with a CLI shim; no importable in-repo package is guaranteed and the CLI is the verified interface. (b) OpenAI-compatible proxy mode (`hermes proxy`) — rejected: a persistent sidecar adds failure modes and would re-implement the agent loop in our code (violates "no second agent framework"). (c) Mocked/simulated agents — forbidden by spec (FR-003/FR-013) and project rules.

## 2. Tool events come from live `stream-json` parsing (1:1, as they happen)

- **Decision**: Run steps with `--format stream-json` (newline-delimited JSON events, implies `--quiet`). The adapter reads stdout incrementally and maps, per the schema family observed in the pre-flight session log: `tool_execution_start {toolName, args}` → emit `tool_started {tool_name, action}`, `tool_execution_end {toolName, result}` → emit `tool_completed {tool_name, status, summary|error}`; the final assistant message text is the step's output. A `--usage-file`/session id, if present in the stream, is recorded on the step run record for auditability.
- **Rationale**: FR-013 requires 1:1 correspondence with real occurrences and US2 wants activity "as it happens"; streaming the executor's own tool lifecycle events is the only way to get real tool success/failure without inferring from final text. F4's `app.js` already renders exactly these event types and accepts the `tool_name/name/tool`, `action`, `status`, `summary/result/output/error` key families (pinned in `contracts/agent-event-payloads.md`).
- **Verification task (bounded, not a pre-flight re-run)**: the exact stream-json envelope for the *Hermes* CLI (vs. the pre-flight harness log) must be confirmed once during implementation with a single trivial opt-in invocation (`F5_REAL_E2E=1` test or one manual `hermes chat -Q --format stream-json -t terminal -q "..."`); the adapter isolates this in one parser module so schema drift cannot leak into the runner. This is covered by tasks and does not re-open the model decision.
- **Alternatives considered**: (a) `--format text` + regex for tool mentions — rejected (fabrication risk; violates 1:1). (b) Post-hoc session dump parsing — rejected (events would lag and depend on session-file locations).

## 3. Tool restriction per profile (least privilege)

- **Decision**: Researcher runs with `-t terminal` (the single pre-flight-verified tool); Critic and Summarizer run with toolsets disabled via the pinned tool-free literal **`-t none`** (pre-flight-probed with exit 0; the CLI prints a benign `Warning: Unknown toolsets: none`, which the adapter ignores — never surfaced as step output or as a failure. Encapsulated as `AgentProfile.toolsets = "none"`. Confirmation that a `-t none` step yields zero `tool_execution_*` events is assigned to the same bounded invocation as §2 and owned by T072, before T080 relies on tool mapping — the contract test asserts zero `tool_execution_*` events for tool-free steps). Additionally each profile's system/task framing states its role boundaries; agents cannot alter workflow, tools, or limits because those are fixed by the runner (FR-007).
- **Rationale**: Operator answer (least privilege, FR-022) + PRD §6 ("agents must not grant themselves additional tools"). CLI-level toolset restriction is enforcement, not convention.
- **Alternatives considered**: Granting all profiles all tools with prompt-level instructions — rejected (unenforced, violates FR-007/FR-022).

## 4. Serial runner as background execution + in-process CLI (one code path)

- **Decision**: `SerialWorkflowRunner` owns the loop: validate mission → compose task for step *i* (objective + `branch_context.current_branch_instruction` for the Researcher, explicitly noting "no audience decision applied" when absent) → emit `agent_started` → execute via adapter (streaming tool events) → validate output (non-empty, ≤ 20,000 chars) → store `AgentRunRecord` → emit `agent_completed` → emit `agent_handoff {from, to, reason}` → advance. API path: `POST /api/missions/{id}/run` starts the runner in one daemon worker thread (module-level lock enforces the single-active-mission cap, FR-009) and returns the mission; CLI path: `python -m backend.app.cli run "topic"` drives the *same* runner synchronously and prints each event line to the terminal (FR-017 terminal-first acceptance). The single-active-mission lock is module-level, i.e. **in-process**: a CLI run concurrent with a server run lives in a different process and bypasses the cap — accepted and documented as a limitation in contracts/workflow-api.md (no cross-process flock guard in F5; F1–F4 stay frozen).
- **Rationale**: One runner guarantees the terminal acceptance path and the dashboard path execute identical logic; F1's controller stays the state-machine owner (`start/complete/fail` + new narrow `advance_step`/`retry` transitions) and never touches subprocesses. Single-threaded serial execution matches PRD §6 (one active mission, one active agent).
- **Alternatives considered**: (a) FastAPI `BackgroundTasks`/async task queue — rejected (adds framework surface; a plain worker thread is sufficient for one serial mission and keeps Ctrl-C/termination semantics simple). (b) Running the loop inside the request handler — rejected (blocks HTTP; SSE dashboard must stay live during a run).

## 5. Abort-to-failed + retry-resume (operator-confirmed reconciliation)

- **Decision**: Any step failure (timeout, non-zero exit, tool failure surfacing as step failure, empty/oversized output, model error) raises a typed `AgentStepError`; the runner emits `agent_failed {profile, step_id, error}` and calls `controller.fail(...)` → mission reaches the FAILED terminal state immediately; the remaining chain never runs; completed `AgentRunRecord`s and the failure reason persist on the mission. `POST /api/missions/{id}/retry` validates status==failed, re-validates the quota gate + model pin, then calls the controller's narrow `retry` transition — the controller owns the `failed` → `running` status flip and emits `mission_resumed {resumed_step, retry_count}` (an existing F4-rendered type; F1's pause→resume keeps the key-less payload — presence of `resumed_step`/`retry_count` discriminates the two meanings). The runner then sets `current_step_index` to the failed step and re-enters the loop at that step with the stored prior outputs composed into its task input — no `agent_started` for completed steps (SC-010). A fresh full re-run is only ever a new mission.
- **Rationale**: Directly encodes the spec's binding reconciliation (FR-020 + FR-021) and its testable consequences; reusing `mission_failed`/`mission_resumed` keeps FR-012 intact (F4 renders both today).
- **Alternatives considered**: (a) "Pause then resume" semantics for failures — rejected (operator chose failed-terminal, not paused). (b) New event types for retry — rejected (F4 protocol frozen).

## 6. Timeout and cancellation mechanics

- **Decision**: Per-step wall-clock timeout (default 300s, configurable via `F5_STEP_TIMEOUT_SECONDS`) enforced by the adapter: the subprocess runs in its own process group and is killed (SIGTERM → SIGKILL after 5s grace) on expiry, raising `AgentStepTimeout`. Inner bounds: `--max-turns` (default 8) and `--run-budget` (default 240s) keep a single step from burning quota even before the outer timeout. The runner registers a `threading.Event` per active mission; `reset` (and any future cancel) sets it, and the adapter's stream-read loop polls it every 0.5s and kills the subprocess — reset during execution leaves no orphan run (edge case). The runner also re-checks mission status before each step boundary.
- **Rationale**: PRD §8 failure behavior (stop the affected step safely) + spec edge cases (reset during execution, no hang). Pre-flight measured 12–15s wall for a trivial turn, so a 300s default leaves ~20× headroom for tool-using research steps while bounding worst-case demo damage.
- **Alternatives considered**: Relying only on `--run-budget` — rejected (it bounds model time, not process wall time; a wedged subprocess must still be killable).

## 7. Quota gate + usage controls (PRD §8)

- **Decision**: `QuotaChecker` runs `hermes usage --json` (verified flag exists; exit 1 when no credential) and extracts the monthly window's remaining percentage. Defaults: warn visibly at start when remaining < 50%; **block** start/retry when remaining < 35% (configurable `F5_QUOTA_BLOCK_THRESHOLD`) unless the request carries `confirm_low_quota=true` (FR-024/SC-011) — HTTP 409 with a clear message otherwise. Result cached 60s to avoid CLI-spam. Usage-control mapping: request cap = `--max-turns` per step; token cap ≈ max-turns × per-turn output bound (documented; Hermes exposes no per-call token flag), plus the 20k-char output bound; simultaneous-task cap = runner lock (one mission, one active agent); operator shutdown = Ctrl-C on the CLI path / reset-cancel on the server path; warning = quota snapshot recorded on the mission + printed/emitted before execution.
- **Rationale**: The pre-flight showed monthly 34% remaining — below the 35% default — so the gate is live-relevant on day one; `hermes usage --json` is the same source the pre-flight trusted. Failing *open* when usage cannot be fetched (credential hiccup) with a visible "quota unknown" warning was chosen over fail-closed: the gate targets *known*-low quota, and blocking a local demo on an unfetchable counter would create a silent no-op risk of its own. Both behaviors are pinned by tests.
- **Alternatives considered**: (a) Hard-code the 34% figure — rejected (window resets; must read live). (b) Fail closed on unknown — rejected for a local single-operator demo; documented trade-off.

## 8. Resolved-model pin (FR-011 enforcement)

- **Decision**: Before every run/retry, `modelinfo` executes `hermes config get model` and requires `default == muse-spark-1.3-contributor` and `provider == opencode-go` (the pre-flight-verified pair); mismatch → refuse start with an error instructing the operator to re-run the PRD §8 pre-flight (no silent model switch, PRD §8). The resolved model string is stored on the mission record (`resolved_model`) so SC-009 is satisfied from the record alone.
- **Rationale**: The pre-flight flagged that the runtime profile override silently differs from config.yaml's static default (`anthropic/claude-opus-4.6`); pinning the *resolved* value is the only honest enforcement of "any model change ⇒ re-pre-flight".
- **Alternatives considered**: Trusting config.yaml — rejected (would verify the wrong model). Auto-reverting to the pinned model — rejected (silent switch masquerading as the original).

## 9. Test strategy (quota-free gates, one opt-in real E2E)

- **Decision**: `AgentExecutor` is a small protocol (`run(step_ctx, emit) -> AgentStepResult`); all unit/integration tests inject a `FakeExecutor` (scripted outputs, scripted tool events, scripted failures/timeouts) — zero model quota, sub-second runs (FR-023). New pytest marker `real_e2e` registered in `pyproject.toml`; `tests/test_agent_e2e_real.py` is additionally gated on `F5_REAL_E2E=1` and skips otherwise, runs exactly one real serial mission (tiny topic, Researcher tool use bounded), and asserts the persisted event log shows three ordered executions and handoffs. Default `uv run pytest -q` never touches it. The 57-test baseline stays green untouched (FR-019).
- **Rationale**: Operator answer (stub + opt-in real) and PRD §8 quota risk; marker+env double gate prevents accidental quota burn in CI/gate runs.
- **Alternatives considered**: Respx/subprocess monkeypatching of `hermes` binary — partially used at the adapter boundary (a fake `hermes` executable fixture for subprocess-shape tests), but the runner tests stub at the protocol level for speed and clarity.

## 10. Task composition and output contracts (PRD §6 role I/O)

- **Decision**: Profile definitions (data, not code paths) pin per-role instructions and expected sections: Researcher → findings, sources, uncertainties, handoff note; Critic → issues, evidence, remaining uncertainty, review; Summarizer → main conclusion, key findings, caveats, what-the-agents-actually-did. Task assembly (documented in `contracts/hermes-executor.md`): Researcher input = mission objective (title/topic) + branch instruction or explicit no-decision note + role instructions; Critic input = role instructions + Researcher's full output; Summarizer input = role instructions + both prior outputs. Handoff bounds: prior output is truncated to the 20k-char bound before composition (bounded payloads edge case). Summarizer output becomes `result_summary` (truncated to the model's 5000-char mission field) — never synthesized by the coordinator (FR-008, acceptance #4).
- **Rationale**: FR-004/FR-005/FR-006 + SC-002/SC-003; section-shaped prompts make the outputs auditable against PRD §6.
- **Alternatives considered**: Free-form single prompt for all roles — rejected (no verifiable role I/O, weakens Critic/Summarizer value).
